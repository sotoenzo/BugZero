Fundamentos de Calidad

La calidad del software es el grado en que un producto satisface necesidades y requisitos. Conocer sus características y métricas ayuda a evaluar el producto y a tomar decisiones durante todo su ciclo de vida.

Elegí un estándar:

ISO/IEC 9126 · Calidad del producto de software

Este estándar organiza la calidad del producto en características evaluables. Sirve como referencia para analizar si el software cumple su propósito y resulta adecuado para las personas que lo utilizan.

Conceptos clave de calidad

  • Funcionalidad: funciones adecuadas para las necesidades especificadas.
  • Fiabilidad: funcionamiento estable y consistente bajo condiciones definidas.
  • Usabilidad: facilidad para comprender, aprender y utilizar el producto.
  • Eficiencia: rendimiento en relación con los recursos utilizados.
  • Mantenibilidad: facilidad para analizar, modificar y probar el software.
  • Portabilidad: facilidad para adaptar o trasladar el producto a otros entornos.

Métricas de calidad

  • Cobertura de pruebas: proporción de requisitos o código cubiertos por pruebas.
  • Densidad de defectos: defectos encontrados en relación con el tamaño del producto.
  • Tiempo de resolución: tiempo promedio necesario para corregir un defecto.

Las métricas se interpretan según el contexto, los objetivos y el método de medición acordado.

ISO/IEC 25000 · Serie SQuaRE

SQuaRE (System and Software Quality Requirements and Evaluation) reúne guías para especificar requisitos, medir y evaluar la calidad de sistemas y productos de software. La serie amplía y organiza el trabajo de calidad en distintas normas relacionadas.

Conceptos clave de calidad

  • Adecuación funcional: grado en que las funciones satisfacen las necesidades previstas.
  • Eficiencia de desempeño: rendimiento en relación con el tiempo de respuesta y los recursos.
  • Compatibilidad: capacidad de coexistir e intercambiar información con otros sistemas.
  • Capacidad de interacción: facilidad de uso, aprendizaje y accesibilidad para las personas.
  • Fiabilidad: capacidad de mantener el funcionamiento esperado.
  • Seguridad: protección de datos y control de acceso a la información.
  • Mantenibilidad y flexibilidad: facilidad de modificar y adaptar el producto.

Métricas de calidad

  • Cobertura de pruebas: proporción de requisitos o código cubiertos por pruebas.
  • Densidad de defectos: defectos encontrados en relación con el tamaño del producto.
  • Tiempo de resolución: tiempo promedio necesario para corregir un defecto.

Las métricas se interpretan según el contexto, los objetivos y el método de medición acordado.

Técnicas de Aseguramiento de la Calidad

Las pruebas de software ayudan a detectar defectos y comprobar que el producto cumple sus requisitos. Se organizan en niveles según el alcance y utilizan distintas técnicas para diseñar casos de prueba.

Niveles de prueba

Abrí cada tarjeta para conocer su objetivo, alcance y ejemplo.

Comprueban una unidad pequeña del programa, como una función, clase o módulo, de forma aislada.

  • Objetivo: detectar errores cerca de su origen.
  • Responsables: habitualmente, quienes desarrollan el código.
  • Ejemplo: comprobar que una función calcule correctamente un descuento.

Verifican que dos o más módulos, servicios o sistemas colaboren correctamente a través de sus interfaces.

  • Objetivo: encontrar fallos en el intercambio de datos o el uso de interfaces.
  • Alcance: desde la integración de pocos módulos hasta servicios externos.
  • Ejemplo: comprobar que el proceso de compra actualice el inventario.

Evalúan el sistema completo en un entorno representativo para comprobar sus requisitos funcionales y no funcionales.

  • Objetivo: validar el comportamiento del producto como un todo.
  • Alcance: flujos completos y características como rendimiento o seguridad.
  • Ejemplo: completar una compra desde el inicio de sesión hasta la confirmación.

Técnicas de diseño de pruebas

Las técnicas de caja negra y caja blanca describen cómo se diseñan los casos de prueba; pueden aplicarse en distintos niveles.

Los casos se diseñan a partir de requisitos, entradas y salidas esperadas, sin depender de la estructura interna del código.

  • Técnicas habituales: clases de equivalencia y análisis de valores límite.
  • Útil para: validar funcionalidades desde la perspectiva de quien usa el producto.
  • Ejemplo: probar límites válidos y no válidos de un formulario de registro.

Los casos se diseñan con conocimiento del código para ejercitar instrucciones, decisiones, caminos o condiciones internas.

  • Técnicas habituales: cobertura de sentencias y cobertura de decisiones.
  • Útil para: detectar lógica no ejercitada y revisar rutas importantes del programa.
  • Ejemplo: verificar que se recorran las ramas de una validación de acceso.

Enfoque externo

Caja negra: requisitos y resultados observables, sin necesitar conocer la implementación.

Enfoque interno

Caja blanca: estructura del código, lógica y cobertura de los caminos seleccionados.

Idea clave: combinar niveles y técnicas permite observar el software desde distintos alcances y perspectivas.
